# win-bpmn-designer 技术方案

> 基于 Vue 3 + Vite 的 Flowable 流程设计器组件库
>
> 定稿日期：2026-09-11

## 0. 关键决策摘要

| 决策项 | 选型 | 理由 |
| --- | --- | --- |
| 画布内核 | bpmn-js + 自研 Flowable moddle 扩展 | 生态成熟，产出的 XML 严格符合 BPMN 2.0，Flowable 引擎可直接部署 |
| 代码语言 | TypeScript | 对外发布的库，类型提示是使用体验的关键；moddle 扩展结构复杂，类型能挡住很多坑 |
| UI 依赖 | Element Plus 作为 peerDependency | 团队已有技术栈，开发最快；externals 不打进产物，避免宿主双实例 |
| 交付形态 | npm 库 + 内置 playground + 独立可嵌入页 | 覆盖 Vue 宿主与非 Vue 老后台两类集成场景 |

已核对的依赖版本（npm 实时）：`bpmn-js 18.28.0`、`bpmn-moddle 10.2.0`、`diagram-js 15.26.0`、`element-plus 2.14.5`、本机 Node 24.16 / npm 11.13。

## 1. 定位与交付物

一个 **Vue 3 的 Flowable 流程设计器组件库**，三种消费方式共用同一套 `src`：

| 产物 | 入口 | 用途 |
| --- | --- | --- |
| npm 包（ES + UMD + d.ts） | `src/index.ts` | 宿主 Vue 项目 `import { BpmnDesigner }` 或 `app.use(WinBpmnDesigner)` |
| playground 示例站 | `playground/main.ts` | 本地 `dev` 调试 + 部署成在线文档/演示 |
| standalone 可嵌入页 | `standalone/main.ts` | 产出单页 HTML，老后台系统用 `<iframe>` + postMessage 集成 |

三个独立 vite config，`build` 脚本串行执行，互不干扰。

## 2. 依赖策略

```jsonc
{
  "peerDependencies": { "vue": "^3.4.0", "element-plus": "^2.9.0" },
  "dependencies": {
    "bpmn-js": "^18.28.0",      // 内核，作为实现细节由本库锁定
    "bpmn-moddle": "^10.2.0",
    "diagram-js": "^15.26.0",   // 显式声明，供自定义模块 import
    "min-dash": "^5.1.0",
    "min-dom": "^4.2.0"
  }
}
```

- `vue` / `element-plus` → peer + rollup external，**绝不打进产物**，避免宿主出现双实例。
- `bpmn-js` 系列 → **ES 产物 external**（交给宿主打包器 tree-shake 与去重），**UMD 产物 inline**（保证 `<script>` 场景开箱可用）。在 `vite.config.lib.ts` 中按 `format` 动态决定 `external`。
- external 用**函数**而非数组：CSS 必须始终参与打包，否则 `bpmn-js/dist/assets/*.css` 会被正则拦成 external，`dist/style.css` 里就会缺掉画布样式。
- CSS 单独产出 `dist/style.css`。图标字体用 `bpmn-embedded.css`（base64 内联）而非 `bpmn.css`，消费方不必处理字体文件的相对路径，`dist` 下也不会多出 assets 目录。
- `package.json` 的 `sideEffects` 必须覆盖 `**/styles/index.ts`，否则 rolldown 会把纯样式入口当成无副作用模块摇掉，`dist/style.css` 直接不生成。

## 4. 核心架构

### 4.1 Flowable moddle 扩展（本库最核心的资产）

社区没有官方维护的 `flowable-moddle`，需自行编写 `core/moddle/flowable.json`，`uri: "http://flowable.org/bpmn"`，`prefix: "flowable"`。需要覆盖的面：

- **UserTask**：`assignee` `candidateUsers` `candidateGroups` `dueDate` `formKey` `skipExpression`
- **ServiceTask**：`class` `expression` `delegateExpression` `resultVariable` `type`（mail / http / dmn）
- **Process**：`candidateStarterUsers` `candidateStarterGroups` `processCategory`
- **通用**：`async` `exclusive` `FailedJobRetryTimeCycle`
- **扩展子元素类型**：`ExecutionListener` `TaskListener` `Field` `String` `Expression` `FormProperty` `In` `Out` `DataAssociation`

XML 模板层面另外固定两点，否则引擎部署会出问题：

1. `targetNamespace="http://www.flowable.org/processdef"`；
2. 导出时的 `bpmn:` 前缀策略与 Flowable Modeler 对齐。

往返一致性用 XML 快照测试兜住。

### 4.2 Vue ↔ bpmn-js 桥接（**最大的技术风险点**）

bpmn-js 是命令式的，且大量依赖对象引用相等（`===`）判断。把 moddle 元素塞进 `reactive()` 会被 Proxy 包裹，导致 bpmn-js 内部比较失败、渲染错乱。约束死三条规则：

1. modeler 实例与 element 一律 `shallowRef` + `markRaw`，**绝不深度响应式**。
2. **数据流入**：`eventBus.on(['selection.changed', 'element.changed', 'commandStack.changed'])` → 更新 Vue 的 ref → 面板重渲染。
3. **数据流出**：所有写操作必须走 `modeling.updateProperties` / `modeling.updateModdleProperties`，**禁止**直接 `element.businessObject.xxx = v`。否则撤销/重做、脏标记、XML 序列化会全线失效。由 `helpers/extension-elements.ts` 把这层封死，面板组件只调 helper。

### 4.3 属性面板：Vue 原生 + schema 注册表

不复用 `@bpmn-io/properties-panel`（它基于 Preact，与 Element Plus 在样式、表单校验、i18n 上混用都很别扭）。改为自研，用注册表驱动：

```ts
registerPropertyGroup({
  id: 'flowable-user-task',
  match: (el) => is(el, 'bpmn:UserTask'),
  order: 20,
  component: UserTaskGroup,   // 或 fields: [...] 的声明式 schema
})
```

内置组按元素类型自动匹配；业务方可注册新组、隐藏内置组、向内置组插入字段。这是这个库能被复用的关键。

### 4.4 业务集成扩展点（决定这个库好不好用）

真实项目里 `assignee` 从来不是手填字符串，所以对外开一组 **resolver 插槽**：

```ts
<BpmnDesigner :resolvers="{ userPicker, groupPicker, formPicker, expressionEditor, classPicker }" />
```

未传时降级为普通输入框；传入时渲染宿主自己的选人弹窗 / 表单选择器。同时暴露具名 slot 覆盖 toolbar、panel-header 以及任意 group。

### 4.5 对外 API

```ts
// 声明式
<BpmnDesigner v-model:xml="xml" :options :readonly :locale :resolvers
              @ready @change @element-select @save />

// 命令式（ref 暴露）
importXML(xml) / createNew(opts) / exportXML({ format }) / exportSVG()
undo() / redo() / zoom(n) / fitViewport() / validate() / getModeler()
```

`getModeler()` 是逃生舱：任何本库没覆盖的能力，业务方可直接拿原生 modeler 操作。

### 4.6 standalone iframe 协议

`postMessage` 双向通信，带 origin 白名单校验：

- host → iframe：`designer:load`（携带 xml）、`designer:request-save`、`designer:set-readonly`
- iframe → host：`designer:ready`、`designer:change`（脏标记）、`designer:saved`（xml + svg）、`designer:error`

## 5. 构建与工程化

- **TS 迁移**：`src` 全量 `.ts` / `<script setup lang="ts">`，`vite-plugin-dts` 产出 `.d.ts` 并 rollup 成单文件。bpmn-js 18 自带类型，缺失处在 `src/types/shims.d.ts` 补。
- **Vite 8 注意点**：内置打包器已换成 rolldown + oxc，`build.minify: 'esbuild'` 不再可用（esbuild 需要单独安装），改用默认的 oxc 压缩；`vite-plugin-dts` 5.x 的选项名是 `outDirs` 而非 `outDir`。
- **Vite 8 + CJS 依赖**：bpmn-js 生态部分包为 CJS，dev 下用 `optimizeDeps.include` 显式列出，避免预构建抖动。
- **测试**：Vitest + happy-dom。重点覆盖两类——XML 导入/导出往返一致性（快照），以及 extensionElements 的增删改 + undo 后的状态还原。
- **发布**：`exports` 字段区分 `import` / `require` / `types` / `./style.css`，`sideEffects: ["*.css"]`。

## 6. 实施路线

| 阶段 | 内容 | 产出验收 |
| --- | --- | --- |
| **M0** | TS 化脚手架、三套 vite config、lib 构建链路、目录骨架 | ✅ 已完成：`npm run build` 三套产物齐全，可 link 到宿主项目使用 |
| **M1** | Modeler 封装、导入/导出/新建、工具栏、palette 与 context-pad 汉化裁剪 | 能画图、能导出合法 BPMN XML |
| **M2** | flowable.json descriptor、桥接层、属性面板框架、基础属性组（Process / 通用 / UserTask / SequenceFlow 条件） | 画出的图带 flowable 属性，可部署到 Flowable 引擎跑通 |
| **M3** | 执行/任务监听器、多实例（会签）、表单属性、ServiceTask、子流程、边界事件 | 覆盖常见审批流的全部建模需求 |
| **M4** | resolvers / slots / group 注册表 / 只读预览模式 / standalone + postMessage | 业务方能接入自己的选人组件 |
| **M5** | i18n、类型完善、单测、README + playground 文档、发布 CI | 可对外发版 |

M0–M2 是让它「能用」的最小闭环。建议先把这三步跑通，拿一份真实流程 XML 丢进 Flowable 引擎验证部署成功，再继续往后推进。
